# Implementation Plan: News Builder Port with Word Import and In-App Photo Editing

**Branch**: `001-news-builder-port` | **Date**: 2026-09-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-news-builder-port/spec.md`

## Summary

Rebuild the Python `news-builder` as a Rust workspace: one domain crate holding every rule, a
Tauri desktop application carrying the editing workflow, and a thin CLI for repeat publishing.
The domain crate imports `.docx`/`.txt`/`.md` (including images embedded in Word and their
positions), processes photos, renders an inline-styled HTML fragment, and publishes photos over
SFTP into a per-item remote folder.

The design turns on one decision: the preview must match the export exactly (FR-022), so the
frontend is a real HTML renderer. Tauri gives that for free — the Rust core renders the
fragment, the webview displays that same fragment in a sandboxed iframe, and no second renderer
exists to drift. The same choice makes the crop control, drag-and-drop, and the "красивый UI/UX"
requirement ordinary work rather than custom widget engineering.

Photo framing solves the cut-off-heads problem without machine learning: crops are opt-in, and
where a layout forces a crop, the frame is anchored with headroom bias toward the top of the
image instead of centred.

## Technical Context

**Language/Version**: Rust (stable, edition 2024), pinned via `rust-toolchain.toml`. Frontend in
TypeScript with Svelte 5 and Vite.

**Primary Dependencies**:

| Concern | Choice |
|---------|--------|
| Desktop shell | `tauri` 2.x + `tauri-plugin-dialog`, `-fs`, `-clipboard-manager` |
| Editor surface | TipTap (ProseMirror) with `svelte-tiptap` node views |
| DOCX reading | `zip` + `quick-xml` (purpose-built reader, see research.md) |
| Image geometry & codecs | `image`, `kamadak-exif`, `webp` (libwebp) for lossy WebP |
| SSH / SFTP | `russh` + `russh-sftp` (pure Rust), `tokio` |
| Credential storage | `keyring` 3.x |
| Errors, logging, config | `thiserror`, `tracing`, `serde` / `serde_json` |
| CLI | `clap` (derive) |

**Storage**: Local files only. Appearance and server configurations are JSON under the OS
config directory; passwords and key material live in the OS secret store, never in those files.
No database.

**Testing**: `cargo test`. Reference-parity golden fixtures under `fixtures/`, regenerated by a
harness that runs the Python reference. Port traits are faked in tests; one opt-in end-to-end
test runs against a local `sshd`.

**Target Platform**: Windows 10+ and Linux desktop (GNOME/KDE). macOS builds are best-effort and
not part of the acceptance set.

**Project Type**: Desktop application plus a supporting CLI, over a shared domain library —
a three-crate Rust workspace.

**Performance Goals**: Preview refresh after a text edit under 150 ms. Full preview rebuild for
a 30-photo item under 1 s using cached thumbnails. Processing one 12-megapixel photo to the
upload budget under 1.5 s. Publish time is network-bound.

**Constraints**: Byte-identical output for identical input (constitution IV). Everything except
publishing works offline. No password or key material in any file the application writes,
in logs, or in error text. Output HTML carries inline styles only.

**Scale/Scope**: Single user, single machine. News items up to ~30 photos. Roughly five screens
in the desktop application.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Gate | Status |
|-----------|------|--------|
| I. Port Fidelity First | Ported behaviour is asserted against goldens captured from the Python tool; every divergence is listed below | **PASS** — deviations enumerated and each traces to an approved spec decision |
| II. Core Library, Thin Frontends | All domain rules live in `newsbuilder-core`; CLI and Tauri layers only adapt | **PASS** — see Structure Decision; the TypeScript layer holds no domain rule and never renders the fragment itself |
| III. Test-First Against Reference Fixtures | Golden fixtures exist for rendering, slug transliteration, marker parsing, natural sort, and path building, produced by a capture harness before the Rust code is written | **PASS** — `tools/capture-reference/` is task 1, ahead of implementation |
| IV. Deterministic Output, Isolated Side Effects | Filesystem, transport, secret store, and clock sit behind traits in `core::ports`; dry-run is a mode of the normal build; uploads converge | **PASS** |
| V. Explicit Errors, No Panics, No Leaked Secrets | `thiserror` types throughout; `clippy::unwrap_used` / `expect_used` / `panic` denied in the core crate; secrets held in a redacting wrapper that cannot be formatted | **PASS** |

### Declared deviations from the reference (Principle I)

Each is an approved decision from the spec's clarification round, recorded here as principle I
requires:

1. Six appearance presets reduced to one built-in appearance (FR-025, FR-035). The configuration
   loader still accepts the reference's `styles` + `image` JSON schema, so the existing
   `style-presets/*.json` files load unmodified as required by the constitution — the product
   simply no longer ships a menu of them.
2. Standalone full-page HTML export dropped (FR-035); the live preview replaces it.
3. Fallback upload through an external `ssh` binary dropped (FR-035); one SFTP path only.
4. The CLI no longer offers arrangement or editing flags (FR-036 – FR-038); it builds and
   publishes an already-arranged item.
5. Credentials move from a plaintext JSON file to the OS secret store (FR-040 – FR-042). This is
   stricter than constitution principle V, which permits opt-in plaintext at 0600; being
   stricter raises no conflict.
6. Word import now derives placements from embedded image positions (FR-002, FR-003), a
   capability the reference does not have. Marker documents are unaffected (FR-005).

### Post-design re-check

Re-evaluated after Phase 1. No gate moved. The two costs worth naming are recorded in
Complexity Tracking rather than waved through.

**Structure Decision**: Three crates, exactly as constitution principle II prescribes.
`crates/core` owns every rule and is compiled and tested with no CLI, no Tauri, and no network.
`crates/cli` and `crates/desktop` are adapters over it: they construct port implementations,
call `core::build`, and present the result.

Publishing deliberately does **not** get its own crate. It lives in `core::publish` behind the
`Transport` trait, which keeps the core independently testable without adding a fourth crate the
constitution would have to justify.

The TypeScript layer under `crates/desktop/ui` is presentation only. It never composes HTML for
the news page: it asks the core for the rendered fragment and puts that exact string into a
sandboxed iframe. This is what makes "the preview matches the export" true by construction
rather than by discipline.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| A TypeScript/JS frontend inside a Rust project (Tauri), adding a Node toolchain to the build | FR-022 requires a live preview that matches the exported fragment, and FR-012 requires an interactive crop frame. A webview *is* an HTML renderer, so preview fidelity is structural | An all-Rust GUI (egui, Iced, Slint) would have to reimplement HTML and CSS rendering to preview the fragment, or ship a second renderer that drifts from the export. Neither can satisfy FR-022 honestly. The Node toolchain is confined to `crates/desktop/ui` and is absent from `core` and `cli` |
| A C dependency (`libwebp`, via the `webp` crate) in the photo pipeline | Sources arriving as `.webp` must be re-encoded lossily at a target quality to meet the size budget while keeping their extension, which parity requires. The pure-Rust `image-webp` encoder is lossless only | Transcoding `.webp` sources to JPEG would change published file names and therefore URLs, breaking parity for those inputs. Refusing `.webp` inputs would fail FR-011. The dependency is confined to `core::photo::encode` behind a cargo feature |
